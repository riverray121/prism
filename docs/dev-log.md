## Notes

- **Cold-start DB race fixed (`library.connect`).** Switching SQLite to WAL takes an exclusive lock and ignores `busy_timeout`, so on a freshly created `library.db` the worker thread and the UI's `library.list` could collide on the switch and one would crash with "database is locked" (worker thread died → no analysis). WAL is a persistent DB property, so `connect` now only switches if not already WAL and tolerates a concurrent setter. Surfaced after wiping the library to start fresh; latent since M2 (a warm DB never contends here).

- **Chords → BTC transformer in M3, not madmom/essentia.** Evaluated [jayg996/BTC-ISMIR19](https://github.com/jayg996/BTC-ISMIR19) (ISMIR'19 bi-directional Transformer, PyTorch). Chosen over madmom (install friction, non-commercial model license, maj/min only) and essentia (AGPL, template-based, finicky wheels): MIT license (code + weights), 12 MB checkpoint, CPU-fine, 170-chord large vocabulary, librosa-CQT input. Cost is the PyTorch dependency — so chords is its own milestone (M3), the first to pull in torch, kept ahead of Demucs (M4) to de-risk torch on a light model before the heavier stage. We vendor its model code (not a pip package); inference replicates its CQT params + checkpoint mean/std normalization + 10s/108-step blocking.
- **Downbeats use a librosa heuristic; improvable later.** Starting with the librosa-based heuristic for `downbeats`. If accuracy isn't good enough, there are better options to upgrade to later (e.g. madmom, a torch model).
- **Model weights → download-on-first-run, never in git.** Pretrained weights (BTC ~12 MB in M3, Demucs ~80–300 MB in M4, PANNs ~80–300 MB in M5) are large opaque binaries — committing them bloats history permanently (git keeps every copy forever, even after deletion) and GitHub hard-rejects files >100 MB. So: a `sidecar/models.py` registry (`{name, url, sha256, dest}`) downloads each model on first use into a gitignored app-data cache (`~/Library/Application Support/Prism/models/`), checksum-verifying so a truncated download fails loudly instead of corrupting analysis downstream. Only BTC needs this hand-rolled (vendored code, no pip auto-fetch); mirror its checkpoint to a GitHub Release on our repo (Releases allow 2 GB/asset, don't count against repo size) so the URL is ours, not a research repo that may rot. Demucs/PANNs auto-download their own weights — just point their cache at the same dir. Chosen over Git LFS: LFS suits team/CI repos that must lockstep-version weights with code; for a solo Mac app it's quota anxiety and setup cost for reproducibility we don't need.
- **All UI design deferred to one M6 redesign.** Through M2–M5 each feature renders into the existing minimal stacked-graph layout, just enough to confirm the data. No dashboard, no shared-axis/zoom consolidation, no layout polish until M6 — the whole UI is designed and built once, against a UI/UX design doc, after the full feature set exists. The duplicated zoom/scrub/playhead code across the three graph components is intentional debt to be paid off then.
- **Sidecar launch: spawn from source.** Tauri's Rust shell spawns `uv run python -m sidecar` as a child process. Reproducibility comes from `uv.lock`, not freezing. Chosen over the Tauri "true sidecar" (frozen binary) because: (1) edit-test loop stays in seconds instead of requiring a PyInstaller rebuild on every Python change; (2) the hard part of freezing is torch/Demucs native libs, which don't land until M3 — so freezing early doesn't de-risk what it would seem to. Do a dedicated freeze spike at M3.
- **Python pinned to 3.12** via uv (not system 3.13). De-risks madmom and essentia, which lag new Python releases and have M-series build friction.
- **No ORM for `library.db`.** Queries are hand-written stdlib `sqlite3`, all isolated in `library.py`; callers never see SQL. Fine while the DB is a single index table. **Shipping caveat:** today the DB is dev-only and gitignored, so a schema change just means recreating it — but if we ever ship to users, changing the schema means real migrations against databases they already have. At that point adopt a migration story (and likely SQLModel, since pydantic is already in use).
- **If we ever want to package/share the app:** the sidecar will need to be frozen into a single executable (PyInstaller or PyOxidizer). The hard part is bundling torch + Demucs native libs — PyInstaller needs manual hook config for those. Tauri then wraps that binary via its official sidecar mechanism (`src-tauri/binaries/sidecar-{target-triple}`). See Tauri docs on sidecar bundling. Plan for a multi-hour spike when this becomes a goal.
  - **Model weights at packaging time.** The download-on-first-run cache (see the weights note above) works as-is for a shipped app — but it makes first launch require a network connection and a few-hundred-MB download (BTC + Demucs + PANNs). Decide then between: (a) keep download-on-first-run (smaller installer, needs network once, must handle download failures gracefully in the UI), or (b) bundle the weights into the installer/app resources (works fully offline, larger download, and the freeze step must include the model files). For a downloadable app, (a) is usually preferred; for an offline/airgapped target, (b). Either way, pin exact weight versions + checksums so a shipped build is reproducible. The cache dir also needs a packaged-app-aware path (Tauri's app-data resolver) rather than the dev-time hardcoded one.
